# M4: Platform (dedicated servers, matchmaking, ranked, replays)

Design doc, 2026-10-17. Status: **proposal + local prototype** (`npm run server`, see §11). Nothing is deployed, nothing costs money yet. Prices were read on 2026-10-17 from the linked pages; "unverified" marks what could not be confirmed from a primary source.

## 0. Summary

- **Server:** a Node process runs many rooms; each room is the *existing* host session (`createSession`, dedicated mode: no seat of its own) driving the same `src/sim`. Clients use the same protocol (v3) over WebSocket instead of PeerJS. Predict mode works unchanged: the server runs stamped inputs at their tick, and nobody has host advantage because the server never plays.
- **Bandwidth decides the cost.** Full snapshots cost **150-300 KB/s per player**; CPU is tiny (**0.04-0.11 ms per tick per room**, under 1 % of a core for 10 players with bots). The host-arbitrated input stream (Option B), whose data the snapshots already carry as `in`, costs **2-8 KB/s per room**. Cross-engine determinism is verified (V8, SpiderMonkey and JavaScriptCore agree on 1,080 checkpoint hashes over 36k ticks), so Option B is safe to build. Ship it before scaling past ~100 CCU.
- **Hosting:** start with **one EU VM with unmetered or 20 TB-included traffic** (OVH VPS-2 or Hetzner CX23), Caddy for WSS, and a domain. That is about **€6-12/month** at 10-100 CCU. Add US East when there are US players. Per-GB platforms (Fly, Railway, Edgegap) only make sense after Option B.
- **Platform features:**
  - The lobby browser and quick play live in the same server process.
  - Ranked 1v1 uses Glicko-2 with placement against bots of known `BOT_ELO`, and needs accounts.
  - Replays are seed + settings + the stepped input stream: kilobytes per match.
  - Spectators already work (the classic stream).
  - P2P host migration is possible but should come late, once dedicated servers cover public play.

## 1. Architecture

### 1.1 Process and rooms

```
browser (predict mode) ──WSS──► server process (Node 24)
                                 ├─ HTTP: /rooms, /health, WS upgrade at /<CODE>
                                 ├─ room ABCDE: createSession(dedicated) + bots + sim
                                 ├─ room QWERT: …
                                 └─ one timer pulse, rooms step from accumulators
```

- **A room** (`src/net/dedicated.ts`) is the normal host session with headless ports:
  - The UI port is a stub store; frame, audio and input are no-ops.
  - Bots come from `src/bots`.
  - A small policy replaces the host's Start button: the first human starts a countdown, results lead to a rematch, an empty room returns to the lobby.
  - Everything else (lobby, reconnect with bot takeover, stamped inputs, snapshots, link monitor, determinism checks) is shared code with P2P.
- **Dedicated mode** in `session.ts`: `openHost({ dedicated: true })` opens the lobby without a seat for the host (`localPlayer = -1`). The fairness delay switches itself off when the host does not play.
- **Rooms per process:** one Node event loop steps every room at 60 Hz from one 4 ms timer. With CPU at about 0.1 ms per tick for 10 players, one core runs about 100 such rooms in CPU terms (60 ticks/s × 0.1 ms = 0.6 % per room). Allow 2-3× headroom for GC, socket writes and spikes: **plan 30-50 busy rooms per core**, one process per core (N processes behind one port via `SO_REUSEPORT`, or a router that pins rooms to processes).
- **Node now, Bun later:** Node runs the code today (`vite-node`, same tooling as the tests). Bun's built-in uWebSockets server would cut socket overhead, but neither runtime is the bottleneck while snapshots dominate. Keep the transport interface; switching is a day of work.

### 1.2 Transport

| | WebSocket (now) | WebTransport (later) | WebRTC data channel (alternative) |
|---|---|---|---|
| Semantics | TCP: ordered, retransmitted. Loss causes head-of-line stalls | QUIC datagrams: unordered, no retransmit | SCTP over UDP, unordered channel possible (what P2P uses) |
| Browsers | all | Chrome, Firefox, Safari 26.4+ (Baseline 2026); older iOS lacks it | all |
| Server side (JS) | trivial (prototype has a 150-line RFC 6455 codec) | not production-grade: `node:quic` experimental, `@fails-components/webtransport` is a native addon, Bun issue open, Deno unstable (2026-10) | `node-datachannel` / geckos.io: works, heavier setup (ICE, UDP port ranges) |
| Through proxies / CDNs | yes | partly | needs TURN for some NATs |

Plan: ship **WSS**. The prototype already handles TCP well enough:
- The transport reports `channel: 'reliable'`, which caps the link grade at 'ok'.
- When the TCP backlog exceeds 256 KB, "unreliable" frames (snapshots, input repeats) are **dropped instead of queued**. A stale snapshot is useless and the next one heals.
- Inputs are redundant anyway: every packet repeats all unacked frames.

Revisit WebTransport when a JS server library is stable. The transport interface (`Transport`, `NetFactory`) already isolates it.

### 1.3 Predict mode against a server

Nothing changes on the client:
- It predicts the whole world about RTT + margin ahead and stamps its frames with the predicted tick.
- The server runs each frame at its stamp: held while early, applied in the next step when late.
- Acked states are bit-identical to the server's, which the 2 Hz determinism check verifies.

Differences from P2P:
- **No host advantage:** the server has no seat, so there is nothing to equalize (§4.4 fairness is P2P only).
- **Lower, steadier RTT:** with a regional server (20-60 ms instead of up to 200 ms to a friend's browser), the lead is 2-5 ticks. Remote corrections are 3-4× smaller than at 150 ms.
- **TCP:** a lost packet delays everything behind it by about one RTT. The client's lead clock absorbs it: late frames widen the margin, and corrections smooth the rest. WebTransport removes this later.

### 1.4 Bandwidth: Option B (host-arbitrated input stream)

**Status 2026-10-17: shipped as M4.2** (`src/net/stream.ts`, default `predict` mode, P2P and dedicated). Measured downlink payload per player at 10 % loss:

| Players | Snapshots | Stream | Ratio |
|---|---|---|---|
| 2 | 150 KB/s | 2 KB/s | 72× |
| 4 | 256 KB/s | 4.3 KB/s | 59× |
| 8 | 231 KB/s | 7.5 KB/s | 31× |
| 10 | 283 KB/s | 9 KB/s | 31× |

On the wire, adding ~70 bytes of UDP/DTLS/SCTP headers per packet, that is 23-36×. Hash-checked 0 desyncs over 10k+ ticks. Details in PLAN §4.4. The analysis below is the design as proposed.

The first table is measured by a scratch harness: dedicated room, bots, memory link, 30 s of fight, Node 24.

| Players | Server CPU per tick | Snapshot downlink per player | Input stream per room (`in`) | Events |
|---|---|---|---|---|
| 2 | 0.041 ms | 153 KB/s (60 Hz × 2.4 KB) | 1.8 KB/s | 2.4 KB/s |
| 4 | 0.067 ms | 269 KB/s (60 Hz × 4.3 KB) | 3.4 KB/s | 5.4 KB/s |
| 8 | 0.091 ms | 254 KB/s (30 Hz × 8.0 KB) | 6.9 KB/s | 4.2 KB/s |
| 10 | 0.114 ms | 298 KB/s (30 Hz × 9.4 KB) | 8.3 KB/s | 5.5 KB/s |

The derived monthly egress below is the snapshot rate × 2.63M s, versus about 5 KB/s for the input stream:

| | Per CCU-month, if averaged over 24/7 | 1,000 CCU |
|---|---|---|
| Snapshots | ~650 GB | ~650 TB/month (≈2 Gbit/s) |
| Input stream | ~13 GB | ~13 TB/month |

Option B: the server already computes everything it needs.
- Each snapshot carries `in`, the exact inputs it stepped, which the client uses for its determinism check. The client already re-simulates from a base with known inputs.
- In input-stream mode the server sends **`in` every tick plus a state hash once a second**, and a full snapshot only on join, on reconnect, on hash mismatch, and every few seconds as a keyframe.
- The client advances its confirmed state by stepping the confirmed inputs. Its predictor rebases from that state instead of from a received snapshot; the code path is the same.
- Events come from the client's own re-simulation, so the events stream disappears.
- Bandwidth falls about 40× (to ~5 KB/s per player in JSON, ~1-2 KB/s with a compact binary encoding).
- Risk: a cross-engine desync. It was checked on 2026-10-17: Node and Chromium (V8), Firefox 149 (SpiderMonkey) and the macOS JavaScriptCore agree on 1,080 checkpoint hashes over 3 × 12k scripted ticks covering 26 spells. The harness lives outside the repo; it should become a CI job (PLAN §11.7). If a desync ever happens, the hash mismatch heals it with a snapshot.
- Delta snapshots are the alternative (diff against the client's last acked state). They are more code than Option B and less saving, so skip them.

### 2.2 Regions and latency

- **EU first** (Germany or France): under 40 ms for most of Europe.
- **US East** (Ashburn / Virginia) second: 10-40 ms on the East Coast, 60-80 ms West Coast. A US West box is only worth it with real West Coast demand.
- **APAC** (Singapore) last: Hetzner and OVH APAC traffic terms are poor for snapshot traffic, so wait for Option B.
- **Region selection:** the client measures WS ping to each region's `/ping` endpoint (3 probes, median), picks the lowest, and shows it with a manual override. P2P remains available for private games with friends.

### 2.3 TLS, ops

- **WSS through Caddy** (automatic Let's Encrypt, `reverse_proxy` speaks WebSocket). Set `stream_close_delay`, or WebSockets drop on every config reload.
- Needs **a domain** (`play.example.com` → the VM). Let's Encrypt has issued 6-day **IP certificates** since 2026-01, an option without DNS (Caddy support unverified).
- Cloudflare proxying in front of the VM works for WebSockets. It saves nothing on egress, adds a hop, and drops sockets on Cloudflare releases, so skip it unless DDoS becomes a problem.
- **Ops:** a systemd unit, a deploy script (rsync + restart), and draining before restart. Draining means stop accepting new rooms and let running matches finish (results arrive within minutes). Also `/health` and a metrics line per minute (rooms, CCU, ms per tick p95, egress), log rotation, and OS updates. About 2 hours per month once set up.

## 3. Lobby browser and matchmaking

- **Directory:** each server process serves `GET /rooms` (public rooms: code, mode, players/max, region, in-match flag) and `GET /ping`. There is no global database at first; the client asks each region's server.
  - P2P hosts could register public rooms with a region server too (heartbeat every 10 s, auto-expire), so the lobby browser lists both kinds.
- **Room privacy:**
  - Private: today's behavior, a code or link.
  - Public: listed.
  - Quick play: the matchmaker assigns.
- **Quick play:**
  - Per region and mode, a FIFO queue fills rooms to the target size.
  - After T seconds (10 s at low population) the room starts and **bots fill the empty seats**. Bots use the difficulty whose `BOT_ELO` is nearest the players' rating (see §4).
  - A human joining mid-match takes over a bot seat (reconnect and bot takeover already exist).
- **Population reality** (PLAN §11.8, a small audience): design for 10-100 CCU. Bots fill seats and quick play is the main entry. No skill-based matchmaking until the queue has people in it.

## 4. Ranked 1v1

**Decided constraints (user, 2026-10-18; built in M4.6, not before):**
- Ranked is **matchmaking only**: an auto-match queue that runs only on dedicated servers. There is no ranked play from custom rooms, P2P hosts or room codes.
- The **server is authoritative**: it records and signs results. Clients never report outcomes.
- **Identity** is the device id for now (`src/game/device.ts`). Accounts are layered on later.
- **Anti-abuse:**
  - One queue entry per device id.
  - Diminishing rating changes for repeated pairings (win-trading).
  - Leaving after a grace period counts as a loss.
  - Bots never affect ranked ratings, except in placement if bot placement stays.
- **Known gap:** smurfing with a new device id, until accounts exist.

- **Rating: Glicko-2**, not Elo.
  - It keeps a rating deviation (RD) per player, so irregular players and newcomers settle fast and the small population isn't punished by slow convergence.
  - Show a conservative rating (μ − 2·RD).
  - Rating periods are daily or per N matches.
- **Placement via bots:**
  - **`BOT_ELO`** (`src/bots/presets.ts`) gives a round-based Bradley–Terry Elo per difficulty, anchored at Medium = 1000: easy 350, medium 1000, hard 1750, brutal 1925, uber 2100. It was meant for a human rating on the same scale.
  - Use that scale: center Glicko-2 at **1000** instead of 1500. The math does not depend on the center; keep 400 points per 10:1 odds.
  - Use **rounds, not matches, as the unit**, as `BOT_ELO` does. A first-to-5 match turns a 75 % round edge into ~90 % of matches; per-match updates would sit on a different scale. Every round of a match is one game in the rating period.
  - Placement is 3 matches against bots. Each round is a game against μ = `BOT_ELO[difficulty]` with a small RD; the next bot difficulty adapts to the running estimate.
  - Later human matches refine it. Bot matches stay unranked after placement (no farming).
- **Authority:** ranked only on dedicated servers. A P2P host could forge results.
  - The server writes the result (winners, rounds, ticks, replay id) to its store and signs it.
  - Clients never report results.
- **Matchmaking:** ±100 window, widening 50 per 10 s. At low population, after 60 s offer "play a bot while you wait" (unranked).
- **Store:** SQLite on the server box at first (ratings, matches, replays index), backed up nightly. One region owns ranked at first to avoid split ratings.

## 5. Replays

- **A replay** is:
  - match settings, slots and seed
  - the **stepped input stream** (`in`: every input the server stepped, by tick)
  - the `connected` patches
  - the sim version (a build id plus a sim-source hash)

  The server builds the stream anyway. Size: 2-8 KB/s of JSON, so about 1-5 MB raw for a 10-minute match, ~100-300 KB gzipped. Binary encoding cuts it further.
- **Version pinning:** a replay only plays on the sim it was recorded with.
  - Store the build id.
  - Keep old builds reachable (GitHub Pages keeps only the latest, so archive `dist/` per release on the server or a bucket), and have the viewer load the matching build.
  - Optional: a golden "replay compatibility" test that pins hashes for a set of replays across releases.
- **Viewer:** a replay driver (like the render dev `simDriver`) steps the sim and feeds `game/frame.ts`. The render, HUD and audio need no change.
  - Seeking needs keyframes: every 10 s a full state, stored in the replay or recomputed on load (36k ticks re-simulate in about 0.3 s).
- **P2P replays:** the host records the same stream, which gives a download button on the results screen at no server cost.

## 6. Spectators

- **Already there:** joining a running match makes you a spectator (`localPlayer -1`). You get the classic interpolated stream, which is smooth and slightly delayed.
- **Server additions:**
  - a "watch" entry in the lobby browser
  - a spectator cap per room
  - for ranked, a **delay buffer** (e.g. 3 s) so a spectator can't call positions to a player
- **Bandwidth:** each spectator costs a player's downlink today (snapshots). After Option B, spectators get the input stream plus keyframes, or a relay process fans out one stream to many viewers.

## 7. P2P host migration

When a P2P host leaves today, the match ends. Migration is possible because every client holds a recent authoritative state:
1. **Detection:** the clients' links to the host close or time out. Each client stops predicting and keeps its newest authoritative snapshot (tick N).
2. **Election:** the new host is the lowest-id human still connected. That is deterministic, so every client picks the same one without talking.
3. **Re-hosting:**
   - The new host re-registers the PeerJS id `brawlock-<CODE>`. The broker frees it when the old peer disconnects; seconds, retry with backoff.
   - It resumes the match from its snapshot N: slots, settings and seed are in the state, and bots are recreated (their memory resets).
   - It marks the old host's slot disconnected (bot takeover per lobby option).
4. **Reconnection:** the other clients re-dial the same code with their reconnect keys. The existing reconnect path seats them, and they resume prediction from the new host's first snapshot.
5. **Cost and risk:**
   - Lost: the ticks between N and the old host's last tick (about one RTT, rolled back) and in-flight inputs (re-sent automatically; they are unacked).
   - Edge cases: a split network (two hosts; resolve by the lowest id when they meet), a broker delay, and the old host returning (it becomes a client).
   - Effort: medium-high. Defer until dedicated servers carry public play, then use it for private P2P rooms.

## 8. Identity, cheating, abuse

- **Identity levels:**
  1. **Anonymous device id** (today: profile id per browser, reconnect key per tab). Enough for casual public play, lobby browser and quick play.
  2. **Accounts** for ranked, ratings across devices and moderation. Options: OAuth (Discord / GitHub / Google), passkeys, or e-mail magic links. Accounts are personal data in the EU (GDPR: privacy policy, data export and delete), which is the main cost, not the code.
- **Authority is already right:**
  - Clients send only inputs, and the server sanitizes them (`sanitizeFrames`, known command shapes, numeric bounds).
  - Stamps are bounded: held ≤ 30 ticks, monotonic, never reordered.
  - Frame and command counts are capped.
  - The state is never client-authored.
  - There is no fog of war, so there is no map hack.
  - Remaining cheats: input automation (scripts that dodge or aim). Detection only: statistics on reaction time and aim, report and review.
- **Rate limits** to add on the server:
  - token buckets per connection (messages/s and bytes/s; drop, then kick)
  - per IP (connections, room creations per minute, joins per minute)
  - a maximum of rooms per process
  - message size limit (prototype: 64 KB per WebSocket message)
  - WebSocket `Origin` check
  - name filter
  - kick and report in the lobby; IP and account bans for ranked
- **DDoS:** OVH's game DDoS protection, or putting Cloudflare in front, are the escape hatches. Not needed at launch.

## 11. M4.1: dedicated server rooms (built)

The prototype grew into the production server. Deploying it is `deploy/README.md`.

- **Rooms:**
  - `POST /rooms` creates a room and `GET /rooms/:code` looks one up.
  - The WebSocket is `/ws?room=CODE`.
  - The first connected human owns the room: lobby edits, start and rematch go to the server as `ctl` messages, and the owner gets the host's controls. When the owner leaves, the next human takes over and the match goes on.
  - A room with nobody connected closes after 60 s.
- **Identity:** a device id (`src/game/device.ts`, localStorage) is sent in `hello`. A returning device reclaims its seat after a browser restart. The per-tab key still covers reloads.
- **Version gate:**
  - The netcode id is a hash of `src/sim` and `src/net`, baked into the client and the server bundle.
  - A release server refuses release clients of another netcode with a "reload" message. `/health` reports the id, so the client marks that region "other version" before it tries to connect.
- **Self-announce:** `welcome.server` marks the link as the server. The connection monitor shows it as the server (`NetStatsView.server`, player id `SERVER_PLAYER_ID` = -1), not as player 0.
- **Regions** (`src/net/online.ts`):
  - Configured by `VITE_GAME_SERVERS` (JSON `[{"id","label","url"}]`). `VITE_GAME_SERVER` is the one-URL shorthand and `?server=` the test override.
  - Each region is probed over `/health`: three samples on the first probe, then one per probe. The ping is the median of the last five. Each region reports its state (up / down / other version / checking), samples, health and load.
  - Auto picks the lowest ping among regions that are up. The region setting can pin one.
  - Joining a code asks every region that is up in parallel and falls back to P2P. Codes have no region prefix, so links stay short and regions can be added without changing codes.
  - Configured now: `us-west` = `wss://brawlock.osc.link` (DigitalOcean SFO3).
- **Hosting is explicit** (user decision):
  - `session.openHost()` is P2P, and `session.openHostServer(region?)` is a server room.
  - Both resolve a typed `HostResult`. A failure carries a reason (`unavailable`, `mismatch`, `full`, `limited`, `error`, `cancelled`) and the other mode's availability, so the UI can offer it in one click.
  - Nothing switches mode by itself.
- **Limits** (`src/net/server.ts`, `src/net/ratelimit.ts`):
  - Rooms per process.
  - Per IP: room creations, lookups, connects and concurrent connections.
  - Per connection: messages/s, bytes/s and message size; a flooding client is cut off.
  - An origin allowlist.
- **Logs:** JSON lines, with IPs only as salted hashes.
- **Ops:** pm2 behind the host's nginx, with a certbot certificate. `deploy/deploy.sh` takes the host, domain and region as variables, so a second region is the same script.
- **Tests** (`src/net/dedicated.test.ts`, real local TCP):
  - Create, own, play, rematch and close a room.
  - A second player is not the owner.
  - Two regions: a code is found on the region that holds it.
  - Device rejoin mid-match.
  - Version refusal.
  - Rate limits.
  - Unknown room.
  - Region probe, median and caching; auto choice; typed failures; config parsing; join routing.
- **Not yet:** metrics beyond logs, more than one process per host.

## 12. M4.3: public rooms, quick play, casual leaderboard (built)

Server rooms only; P2P rooms are neither listed nor rated.

- **Public rooms:**
  - A server room's owner switches it between public and private in the lobby (`ctl` op `visibility`). Rooms with a code are private by default; quick-play rooms are always public.
  - `GET /rooms?public=1` lists the public rooms of one server: code, owner name (none for quick play), humans, bots, max, phase, team and game mode, win score, region. The list is computed at most once per second and limited to 60 requests/min per IP.
  - The client's room browser (`online.browse()`) asks every region that is up in parallel. It lists open lobbies first, then rooms between matches, then running matches, with lower ping first within each. Joining is a plain join by code.
  - **Player-hosted rooms** ("Host from your PC") can be listed too: the lobby's "Listed publicly" switch, off by default (`src/net/listings.ts`, `src/net/lister.ts`).
    - The host registers the room on its region setting (Auto = lowest ping) with `POST /listings`, which returns a listing id and a secret token. It reports the code, host name, players, phase, mode and win score.
    - `PUT /listings/:id` (with the token) is the heartbeat every 10 s, and also carries changes, at most one per 2 s. `DELETE /listings/:id` unlists at once.
    - Without a heartbeat for 30 s the listing drops, for example when the tab closes. A heartbeat to an expired listing (server restart) answers `gone`, and the host lists again.
    - A full room is off the list until a seat frees. A running match stays listed as "In a match", like server rooms, since a joiner watches and then plays the next match.
    - Switching it off, leaving, or any new room makes it private again at once.
    - The server never connects to the P2P host: it is only a directory, held in memory.
    - Listings show in `GET /rooms?public=1` as `listings` next to `rooms`. Browse games merges both, tags PC rooms "Player-hosted", and shows their ping as "–" with the listing region as a rough hint. Joining is the normal P2P join by code.
    - **Abuse controls:**
      - Per IP: 6 listings created per minute, 30 heartbeats per minute, and 3 live listings. At most 500 listings per server, and one listing per room code.
      - Fields are validated and the name sanitized. Bodies are capped at 4 KB.
      - The public view has no id, token, IP or device id.
    - **Never ranked or counted:** a player-hosted game never reaches the leaderboard, which only counts matches a server ran itself.
    - **Known gap:** anyone who knows a private code could list it. Codes are only shared with friends, and a listing gives no more access than the code already does.
- **Quick play** (`POST /quickplay?bots=hard`; the client picks the region as for hosting):
  - The server reuses a public quick-play room with a free or reservable seat, including running matches with bot seats. Active public owner games with reservable bots are eligible too. The fullest room is chosen first, then the oldest.
  - A seat handed out is held for 15 s, so two players who press Quick play together land in the same room even before the first has connected.
  - Otherwise the server creates a room. Manual owner lobbies remain excluded because an idle owner could strand quick players waiting for Start.
  - **Room policy** (`QuickPlayPolicy`, user decision):
    - A room holds up to 10 humans (`QUICKPLAY_SEATS`). Quick play sends the next player to a new room, and a link into a full room is refused.
    - When fewer than 10 humans are in, bots (Brutal by default, or the player's choice) top the table up to 10 players (`QUICKPLAY_BOT_FILL`).
    - One human: the match starts after 10 s.
    - Two or more humans: the match starts after 5 s.
    - A casual game is first to 3 round wins.
    - Between matches nothing starts by itself: players read the results until they press Ready. Everyone ready starts the next match at once; after the first Ready the others get 60 s. Humans who arrive meanwhile replace bots at once, then take free seats up to 10.
    - Leavers are replaced by bots.
    - Abandoned tabs: when a match ends, a human who did nothing during all of it (no input, no chat, at least 3 complete rounds) goes back to the menu with a notice and is not carried into the next match. Nobody is removed during a match; one input or chat line keeps the seat. This applies to every room that runs itself (quick play, ranked queues), so an open tab costs at most the match it was abandoned in: alone it never presses Ready, and with other players it is dropped when the next idle match ends (`RoomOptions.idleRounds`, `src/net/dedicated.ts`).
    - Nobody owns a quick room; the lobby shows the countdown (`lobby.autoStart`, `fill: true` for the one-human countdown).
  - In a running round, a newcomer reserves a bot seat and watches until the next shop/round boundary. The bot finishes the current round; no pawn is resurrected or reassigned during combat. Leaving while waiting restores the reservation to the original bot. The HUD shows persistent waiting status plus join, departure and activation notices. With no bot available, explicit browser joins watch until the next match; quick play selects another room.
  - Pending bot reaction-delay orders are sent ahead as compact tick-stamped plans, repeated against packet loss. Prediction keeps the existing combat timeline while using already-decided bot turns rather than assuming unchanged movement. Schedule replacement and handover clear stale future orders. Human input hints are unchanged.
  - Seat identity changes ride the deterministic input stream and replay before their activation step. New humans enter leaderboard accounting at activation; earlier bot actions are excluded.
  - Not done: rating-based bot difficulty (§3).
- **Casual leaderboard** (`src/net/leaderboard.ts`, `server/leaderboard-store.mjs`):
  - **Recording:** the server records each finished match it ran, and clients never report outcomes.
  - **Identity:** the device id. The board shows the name and a 5-character tag hashed from the id; the id itself never leaves the server.
  - **Rating:** Elo per round on the `BOT_ELO` scale (start 1000 = the Medium bot, 400 points per 10:1 odds, K = 20 per round).
    - Every round ranks its humans: round winners first, then the last to die above earlier deaths. Each pair of humans in a round is one game.
    - A player's change is averaged over their pairs. Teammates are not rated against each other.
    - Deathmatch ranks the whole match by score.
  - **What counts:**
    - At least 2 distinct devices in human seats (a second tab of the same browser shares its device id), at least 2 minutes long, and at least one round between humans.
    - Bots never count: no rating from rounds against them, no kills of them, no deaths to them. Deaths to oneself (lava, own blast) count.
    - A seat a bot took over stops counting from then on.
  - **Storage:** built-in `node:sqlite`, which needs no native dependency. It is unflagged on Node 22.13+ (the host runs 22.22), and pm2 silences its ExperimentalWarning.
    - One file, `/opt/apps/brawlock-server/data/leaderboard.sqlite`, with a WAL journal and one transaction per match.
    - Tables: `matches`, `results` (per device per match) and `players` (running totals).
  - **API:**
    - `GET /leaderboard?period=all|week&region=&device=` returns the top 100 and the caller's line. 'all' is ordered by rating; 'week' by rating gained in the last 7 days.
    - `GET /players/:device` returns a device's profile and its last 10 matches.
    - Pages are cached for 5 s; reads are limited to 60/min per IP.
  - **Per region:** each server keeps its own board, and the client reads the region it would host on. One board across regions needs one region to own it (as planned for ranked, §4).
  - **Known gaps:**
    - Win-trading between two devices of one person (a second browser) is not detected.
    - A new device id resets a player.
