## Authority and identity

Run one account authority on US, shared by US West and Europe. `accounts.sqlite` stores Better Auth users/sessions, reserved profiles, global ranked occupancy and [Embers/cosmetics](PROGRESSION.md). The global rating authority remains separate; its player keys are derived server-side as `a_<account ID>`. Display names, device IDs, email strings and browser storage never prove account ownership.

The regional game bundle calls the account authority over an authenticated server-only link. OAuth code and provider secrets stay in the separate auth bundle. Production game startup requires `ACCOUNTS_AUTHORITY_URL`; authenticated regions also require `DATA_DIR` for durable progression delivery. See [STATIC-HOSTING.md](STATIC-HOSTING.md) for the first-party page and Pages media split.

Better Auth and `@better-auth/passkey` are pinned to 1.7.11. The library owns cookies, OAuth state/PKCE, one-time admission tokens and WebAuthn verification. Cookie caching is disabled: profile and admission requests check the session database. Logout revokes that session. Provider email stays private. Password registration is disabled; start with a configured social provider, then add a passkey. Passkey-only enrollment and recovery are not included. Explicit linking requires an authenticated account and matching provider email; implicit email-based linking is disabled. Passkey enrollment and sign-in require verified PIN/biometric flags, not possession alone.

## Public API and player profiles

All browser endpoints are same-origin and `no-store`; writes require the exact configured Origin and JSON. Browser API paths are `/api/auth/*`, `/api/account`, `/api/account/config`, `/api/account/admission`, `/api/progression*` and `/api/presence`. The direct library one-time-token routes are blocked from browsers.

Authenticated `GET /api/account` returns `{id, email, profile, game}`: a stable account ID, the owner's sign-in email, the reserved name/preferred color or `null`, and an occupied ranked region/room or `null`. Profile writes return the same private shape. Email is shown only to its signed-in owner; it is absent from regional admission, snapshots, leaderboards, public profiles and population counts. Provider credentials and session tokens are never returned here.

`POST /api/account` claims a name/color. `PATCH /api/account` changes the name and color; color-only requests retain the current name. Names use 3–16 ASCII letters, numbers or underscores, start with a letter, normalize NFKC and are unique case-insensitively. Controls, other scripts and reserved system names are rejected. SQLite uniqueness handles competing claims and renames. A successful rename atomically releases the previous name; a conflicting name returns 409 without changing either field. No rename cooldown or old-name hold is imposed; the existing six-per-minute profile-write limiter applies. The provider display name cannot overwrite the game profile. Renames retain the immutable account ID, rating key, ownership and currency.

The Account dialog edits the claimed name and color, displays validation/conflict errors and publishes the server's canonical profile to shared client state. An earlier in-flight identity read cannot replace a newly saved profile. Unsigned players keep their separate guest identity and preferences. In account-enabled dedicated rooms, the server supplies signed-in names and marks unauthenticated names as guests; guest claims using the account identity namespace are rejected.

## Online population

Prepared after `f97de56b685b`: `/api/presence` is a public aggregate separate from regional `/health.players`, which continues to count connected humans in lobbies/matches. A browser sends one small same-origin JSON heartbeat every 30 seconds throughout the app, including menus, offline play and replays. It submits only its existing anonymous browser ID and selected/current region. Account identity comes exclusively from a verified session cookie, never the body. Multiple tabs on one browser count once; multiple signed-in devices count once, assigned to the most recently active region. Region changes update a single authority entry, avoiding cross-region double counting.

Leases expire after 90 seconds without a heartbeat, need no unload request and are held only in memory. A service restart briefly clears presence until visitors refresh their leases; it does not touch accounts or game state. Public responses contain only regional counts and a total. Request shape/size, trusted proxy address, per-IP rate/device limits and total capacity bound anonymous writes. New official regions must be added to `src/shared/presence.ts` as well as the game/workflow fleet configuration. Population is approximate and has no authority over matchmaking, account ownership, Elo or rewards. Failed reads display unknown rather than substituting game counts or assuming zero.

### Persistent operational analytics

Prepared locally for the next release: each authority writes its own private `analytics.sqlite`. The account authority records guest/account activity, browser links, first/last seen, visits, approximate app time and online population. Regions record every dedicated match independently of Elo eligibility: starts, completions, abandonments, interruptions, participation and bot counts, duration, rounds and actual settings. Casual, custom and short games count. A rematch gets a fresh match ID; reconnects do not create another participation. A stopped simulation is marked interrupted only after a replacement process owns its regional port. Analytics write failures log `analytics.write.failed` without suppressing gameplay, Elo or rewards.

The explorer uses the following dimensions:

| Scope | Recorded dimensions and measures |
|---|---|
| App activity | Selected/current region, client-reported app release (`__BUILD_ID__`), client netcode (`__NET_ID__`), screen, guest/account state, deduplicated identities and browsers, first observed guest-to-sign-in transitions, visits and approximate active minutes |
| Dedicated matches | Actual region, server net build, server release commit, queue, game mode, team format, outcome, start/end, completed simulation seconds, rounds, initial bots and human participations (including late arrivals) |
| Operator investigation | Match UUID and room reference, sortable matching-game table, filtered CSV and JSON exports |
| Concurrent activity | Simultaneous segments by region, client release/netcode, screen and guest/account state, sampled at most once per 30 seconds while heartbeats arrive |

Region means the selected/current game region, not geography inferred from an IP. Guest identities represent browser installations; verified account identities deduplicate across devices. The browser total also deduplicates sign-in and sign-out on the same browser. Several browsers can link to one account, and a shared browser can link to several accounts without merging accounts, changing ownership or transferring rewards. Clearing browser storage creates a new browser identity. Historical guest/account states remain separate and overlap; do not add them to count humans. The first observed account sign-in after guest activity on a browser counts as one transition, even for a returning account. It is not a new-registration metric. Signing in/out continues an active visit. Visits restart after 30 minutes away; heartbeat gaps over 90 seconds do not count toward app time. Midnight-crossing time is split across UTC days. Screen reach is not a causal funnel. Offline/P2P match results are not captured.

The interactive report filters by region across both app and match data. App release, client netcode, screen and identity filters affect app metrics. Server build/commit, queue, mode, team format, outcome and “contains player kind” affect matches. Charts, period comparisons, breakdowns and the matching-game list all recalculate from the same filtered records. Rates use the underlying counts, not averages of percentages. Daily, weekly and range uniques deduplicate after filters; weekly peaks take the maximum of simultaneous population, not sums of per-segment peaks. Global observed historical peaks remain available; filtered peaks use the 30-second samples and show gaps before sampling began. Conversion attribution by screen, client netcode and activity identity is unavailable and is shown as such rather than substituted with global values.

Client version/context metadata is validated and used only for analytics. It cannot establish identity, permissions or gameplay results. The presence endpoint accepts the earlier two-field heartbeat during rollout and records missing context as **Unrecorded**. New clients submit release/netcode/screen. Server net builds come from the running configuration and release commits are baked into the server bundle; old match versions are not guessed from the current process. Body limits remain bounded at 512 bytes and the existing origin/session/IP limits still apply. Public presence responses still contain only population totals; version/context segments are private.

SQLite uses WAL/FULL and an independent schema. Schema 2 preserves history and the HMAC key while adding browser/account links. Schema 3 adds traffic context, concurrent samples, server build/commit and room references, preserving existing records. Old app activity retains its known date/person/region and gets unrecorded version/screen attribution; old match metadata remains null. Collection timestamps separately cover base activity, browser links and version/context tracking. Earlier transitions and context are not reconstructed. Upgrades are additive and idempotent; unknown schemas stop startup. Back up consistently before upgrading, including active WAL. Rollback to an older analytics binary requires restoring its pre-upgrade analytics backup, never changing the version marker. Account/rating schemas and data are unaffected by these analytics upgrades.

`GET /internal/analytics?days=30` is private and `no-store`, requires GET and rejects browser Origin headers. Accounts use the existing regional bearer credential; regions use their existing maintenance credentials. There is no public analytics/admin browser role. Report format **3** includes up to twice the requested date window for equal preceding-period comparisons. Private report-specific random identity keys allow exact offline filtering; raw player/browser IDs, persisted identity HMACs, names, emails, IPs, cookies and credentials are absent. Match and room references are retained for investigation. Treat the report as private activity data. Filtered JSON contains counts, breakdowns and matching games; filtered CSV contains the matching games without per-player keys. Old snapshots without the required facts must be collected again.

```sh
npm run analytics -- --days 90
```

The command reads `deploy/release.config.json`, collects the account authority and both regions over SSH, and writes `artifacts/analytics/index.html` and `report.json`. Credentials stay on the hosts. If any source fails, collection fails without overwriting the previous report or presenting partial totals as complete. The standalone HTML makes no network requests. Re-render an existing format-3 snapshot with `npm run analytics -- --input path/to/report.json --out path/to/report-directory`.

The explorer offers Today/7/30/90-day presets within the exported window, custom UTC dates, and Daily/Weekly grouping. Comparisons use the same filters on the preceding equal number of UTC dates and show percentages only when both windows have full history. Today remains in progress. Tabs expose Overview, Regions, Versions, Queues & modes, Audience & screens and Matching games; click a breakdown row to filter. Region/build comparisons show volume, completion, abandonment and average duration together. Live population and registered-account totals are explicitly snapshot/lifetime values, unaffected by historical filters. Keyboard, touch and hover inspection work without a service running.

`node scripts/analytics-demo.mjs` rebuilds a reproducible **DEMO DATA** preview at `artifacts/analytics/demo/index.html`, with changing client/server releases, both regions, mixed modes/queues, screen activity and unrecorded metadata. These are synthetic records, not production statistics. Focused checks include `node --test scripts/analytics-model.test.mjs scripts/analytics-report.test.mjs`, analytics/account/presence tests, additive version-1/2 migrations and the real match/rematch lifecycle. Browser evidence is retained alongside the preview.

Production collection requires the matching account, regional server and client release. This work has not deployed them. Earlier guest visits, casual/abandoned matches or version context cannot be recovered from the narrower Elo ladder.

Leaderboard and public-profile reads resolve the current reserved name from the account authority. Completed matches store their server-verified historical label under the immutable account key; rating commits do not depend on the account service being reachable. An older result therefore cannot revert the visible current name, and a temporary auth outage cannot discard a completed US rating. Account-name lookup failures are explicit rather than displaying a potentially reassigned historical name.

## Regional admission and reconnects

`POST /api/account/admission` requires a valid session and a claimed profile. Its JSON body is `{device, controller, takeover}`: the existing browser ID, per-page controller key and an explicit boolean transfer request. Unknown fields and missing identities are rejected. The first request installs a signed, host-only, HttpOnly, SameSite=Lax browser cookie (Secure in production); later requests use that cookie for device consistency even if JavaScript changes its device ID. It issues a fresh library token for each regional action. Tokens expire after one minute, are stored hashed, consumed once and never persisted in browser storage. A separate hashed-ticket record binds the verified account, pseudonymous device and tab/controller plus takeover intent to the proof; it expires with the token. Regions exchange tokens over `/internal/accounts`; the verified response supplies the immutable ID, canonical name/color, rating key, cosmetic equipment and controller binding. The browser cannot override these through `hello`.

HTTP ranked matchmaking verifies account proof before reserving a seat. Regional WebSocket admission verifies a separate proof before attaching the player; casual guest admission is explicit. No account-service outage silently turns a signed-in ranked player into a guest.

The account authority stores **one global ranked participation per account**, with no time-based expiry that could permit two active ranked matches. A claim for its existing region/process-generation/room is idempotent; another ranked room or region is rejected with the existing game route. Disconnecting from an active ranked game retains its participation for reconnect and anti-abuse. Room/session cleanup releases it. A newly registered regional process generation removes that region's obsolete participation; the region binds its game port before registering, so a duplicate process cannot fence a live one. Participation survives authority restart. This competitive ledger is separate from the all-mode active-game ownership described below.

### One active game across every mode

Prepared locally, schema 5: **one active game per account OR browser device**, including guests, local bot games, guided practice, P2P hosting/joining, casual, custom and ranked. All UI/session entry points acquire the same browser Web Lock before creating a room, reserving a queue seat or starting a local simulation. A duplicated tab has a different controller ID even when its sessionStorage was cloned. The signed device cookie prevents changing the JavaScript device ID alone from bypassing the authority's device check. Menus and replays do not acquire a game slot.

Account-enabled clients also acquire one shared-authority permission through same-origin `POST /api/play`, including guests. Account identity comes only from the verified cookie; anonymous permissions use the signed browser device. SQLite enforces unique device and unique non-null account ownership across both regions. Permissions are opaque random tokens, stored hashed in the authority and held only in client memory. Ten-second heartbeats renew a 30-second permission; a small worker keeps these updates running in background hosting tabs. Local simulations, input wakes and clients stop at a conservative monotonic deadline before authority expiry, independent of wall-clock skew and timer delivery. Account-enabled local play therefore needs this service to start and remain active; there is no outage bypass. Standalone builds without accounts enforce the same-browser rule through Web Locks.

Every account-enabled regional WS join, including guests and non-ranked games, must supply this permission in addition to its optional account ticket. One permission can attach to only one server connection/room/region. A server checks revocation about every five seconds and gates all incoming commands at its conservative expiry deadline. It acknowledges detachment using a unique connection ID and regional generation. Client release alone cannot free a still-attached server connection. Authority restart preserves permissions and connections; a restarted region fences its old connection generation.

The generic **Game already open → Use here** dialog covers all modes. It requests the old owner to yield (immediately across same-browser tabs), then waits for that owner to stop and for any regional connection to detach. An unreachable owner keeps the slot until expiry; the new game cannot start during that wait. Existing dedicated games reopen by their original region/code, preserving the normal seat-reconnect path. Local/practice games restart; P2P hosting ends the old hosted session and warns that its guests will disconnect. Raw identities, account emails and permission tokens are absent from conflict messages. Ranked participation/device reservations still prevent switching accounts to oppose a prior participant in the same ranked session. Browser profiles, cleared site data and different devices cannot establish a unique human identity.

Prepared locally for the next release: ranked admission also reserves each browser device globally. Different accounts cannot occupy a ranked seat on the same browser, even across regions or with tickets minted concurrently before either claim. Reservations are transactional and every device used by that ranked account stays reserved until its ranked room/session releases, including after a transfer. This prevents moving an account away and immediately reusing its old browser as an opponent. Disconnects do not expire the lock; stale regional generations are fenced as above.

A second controller of the same account gets a conflict dialog showing the existing region and game, with **Use here**. That action rejoins the existing game with explicit transfer permission; it cannot start another ranked game or take a different account's seat. The regional host removes the old peer, sends its moved-session message, closes it and preserves the same pawn/score/loadout for the new controller. Removed peers cannot issue subsequent commands. The old tab never automatically takes control back. Each document gets a fresh controller key, so duplicated tabs cannot reuse a cloned sessionStorage reconnect key. The region acknowledges the last controller’s disconnection with its controller ID as a fence. A new document can reconnect normally after that acknowledgement; a delayed old disconnect cannot unlock its replacement. Failed disconnect updates are retried before regional admission proceeds. An unacknowledged connection still requires explicit Use here, rather than expiring a lock on a timer. A different account on an occupied browser gets an explanation without a transfer button. Browsing menus is not an additional ranked seat. Browser/device consistency is an abuse guard, not proof of a unique human: separate browser profiles, cleared site data and separate devices remain outside that guarantee.

`GET /api/account` exposes a ranked route for the main-menu rejoin action only after that account participates in a started match. Waiting queue reservations still enforce exclusivity but do not appear as games to rejoin. The region sends an authenticated, generation/room/participant-scoped `started` notice from the simulation match-start hook through the existing ordered lifecycle retry queue. Leaving a waiting lobby releases its reservation and closes the empty queue room. Disconnecting from an active match retains recovery while that room remains alive. Ordinary reconnect identity guards remain in place. Rating and reward results come from the regional simulation, never browser scores. Progression uses its own durable regional outbox, so official casual matches can earn Embers independently of Elo. See [PROGRESSION.md](PROGRESSION.md) for eligibility, purchase/equip contracts and honest pending/unavailable result states.

## Schema and local operation

Node's built-in SQLite runs with WAL, full synchronization and foreign keys. `accounts:migrate` explicitly applies reviewed library changes and additive application versions: **1 profiles, 2 regions/occupancy, 3 progression, 4 ranked device/controller bindings, 5 all-mode game ownership, 6 started ranked participation**. Re-running migration preserves users, sessions and application data. Normal startup refuses missing/incomplete schema; unsupported versions and unsafe library migrations stop startup. Do not reset `accounts.sqlite` to reset the old ladder. Schema 6 requires the matching account, regional and client release: drain both regions and take the normal consistent backup, migrate the authority, deploy both regions, then publish the matching client and reopen. Legacy tickets/WS handshakes without game permissions fail closed with a reload/verification error. Restore the matching pre-migration backup to roll back to older code; never change the version marker to bypass migration. Schema 6 adds only a `started` flag. Existing occupancy keeps recovery because its earlier phase cannot be reconstructed; new claims explicitly begin unstarted. Analytics stays in its separate SQLite file.

Keep secrets outside the repository and out of every `VITE_` variable. Local configuration:

```
AUTH_ORIGIN=http://localhost:5189
AUTH_PORT=5352
AUTH_DATA_DIR=/private/tmp/brawlock-local-accounts
AUTH_SECRET_FILE=/path/to/private/random-session-secret
AUTH_REGIONS_TOKEN_FILE=/path/to/private/shared-regional-token
AUTH_GOOGLE_CLIENT_ID=<provider client ID>
AUTH_GOOGLE_SECRET_FILE=/path/to/private/google-client-secret
```

At least one provider must be fully configured. Discord/Microsoft use `AUTH_DISCORD_*` / `AUTH_MICROSOFT_*`; a partial provider is a startup error. Register the callback `${AUTH_ORIGIN}/api/auth/callback/google` (or `/discord`, `/microsoft`). The [Google walkthrough](GOOGLE-SIGN-IN-SETUP.md) documents console setup and the production callback.

```
npm run accounts:migrate
npm run accounts
VITE_ACCOUNTS_ENABLED=true npm run dev -- --host localhost --port 5189 --strictPort
```

The explicit Vite opt-in proxies auth, account and progression API paths to loopback port 5352. Use `localhost`, matching the configured Origin. Production requires HTTPS. Auth-library limits are persistent; profile writes, admission and collection changes have separate account buckets. The loopback service bounds streamed bodies to 32 KiB, profile/collection bodies to 1 KiB and private regional requests to 16 KiB. Private requests require a timing-safe bearer check and reject browser Origin headers.

`npm run accounts:build` creates `dist-accounts/accounts.mjs`. The separate [PM2 template](../deploy/accounts.config.cjs) names only `brawlock-accounts`; it does not replace the game ecosystem or operate on other apps. Prepared US paths are `/opt/apps/brawlock-accounts` (root-owned code), its service-writable `data/`, and protected configuration/secrets under `/etc/brawlock/`. Routine updates retain the session secret and consistently back up SQLite/WAL data. `TRUST_PROXY=1` is appropriate only behind the trusted loopback proxy setting `X-Real-IP`.

The supplied Google JSON was validated with the exact callback, PKCE and only `openid email profile`. Secrets and the original JSON remain outside Git/client assets. The public website cutover is complete and the user confirmed the real provider flow.
